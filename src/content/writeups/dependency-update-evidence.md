Updating a dependency changes the software that gets built and deployed. A version bump should therefore be treated as a controlled change, with evidence that the update is understood, reproducible, and recoverable. The scenario below is fictional: the service, package, and measurements are examples, not findings from a real environment.

The team plans to update `jsonfast` from `2.4.1` to `2.5.0` in the fictional `order-api` service. The newer release includes a security fix and a small behavior change in date parsing. The goal is to decide whether the update can be accepted, not to assume that a green build is enough.

## Inventory

Start by identifying where the dependency enters the build. `jsonfast` is a direct dependency of `order-api`, used by the request validation and report export modules. The lockfile also shows it as a transitive dependency of `report-builder`, pinned to the same version range. No other service in the reviewed set uses a conflicting version.

Record the owner, the reason for the update, the affected modules, and the versions in use before and after. Include transitive dependencies, because a direct update can change a shared package's resolved version elsewhere.

## Lockfile

The lockfile must be regenerated by the package manager, committed with the change, and reviewed as code. A hand-edited version string is not acceptable evidence. In this case, the diff shows `jsonfast` moving to `2.5.0`, with no unexpected additions or removals.

Acceptance also requires a clean checkout. Clone the change into a fresh directory, install with the lockfile, and confirm that the resolved version matches the intended one. Record the package manager version used, so another reviewer can reproduce the result.

## CI

The pipeline for the change runs unit tests, integration tests, a dependency scan, and a build. All pass. The scan reports no known vulnerable version in the final lockfile. The changelog is reviewed for the date-parsing behavior change, and the two affected modules are exercised by existing tests.

Passing CI is evidence for this change, not proof that no regression exists. It shows that the tested behavior still works under the tested conditions. Keep the pipeline link and commit SHA in the change record.

## Rollback

Before merging, prepare the recovery path. The previous lockfile and manifest are retained in version control, so reverting the commit restores `2.4.1`. Keep the previously accepted deployment artifact available. Check whether the rollback needs to account for state or schema changes. This fictional update makes neither.

A rollback plan that exists only in a chat message is not evidence. Write the steps, the owner, and the trigger conditions in the change ticket.

## Acceptance record

```text
service: order-api
change: jsonfast 2.4.1 -> 2.5.0
inventory reviewed: yes
lockfile regenerated and committed: yes
clean checkout reproduced: yes
CI passed: yes
rollback commit prepared: yes
reviewer: platform-engineering
```

Dependency updates are routine, but routine work benefits from a record. The inventory shows scope, the lockfile shows reproducibility, CI shows tested behavior, and the rollback path shows recoverability. Together they make the acceptance decision inspectable. See [NIST SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final) and [OWASP Dependency-Check](https://owasp.org/www-project-dependency-check/) for broader software supply chain and component guidance.
